# انتشار برای نگهدارنده

هر مجموعهٔ تغییر باید `VERSION` و بخش متناظر `CHANGELOG.md` را به‌روز کند و از
مسیر PR، بررسی کد و تست‌های لازم بگذرد. پس از ادغام، CI همان commit را آزمایش
و سپس تگ و Release را با `gre4.sh` و `SHA256SUMS` همان commit منتشر می‌کند.
شمارهٔ جاری و تاریخچه در README تکرار نمی‌شوند.

انتشار ابتدا پیش‌نویس است. هر دو فایل پیش از عمومی‌شدن بارگذاری و تطبیق داده
می‌شوند. خواندن‌های شبکه برای خطاهای گذرا و تأخیر دیده‌شدن نتیجه، تلاش مجدد
محدود دارند. خطای دسترسی، مقصد نادرست تگ یا محتوای متفاوت با retry پنهان نمی‌شود.
عملیات نوشتن کورکورانه تکرار نمی‌شود؛ اجرای دوبارهٔ job، وضعیت موجود را بررسی
می‌کند و فقط کار ناتمامِ قابل تأیید را انجام می‌دهد.

## قفل انتشار در GitHub

قواعد مخزن و کنترل‌های publisher مانع بازنویسی فایل‌های انتشار توسط این
فرایند می‌شوند. برای قفل‌شدن تگ و asset در خود GitHub نیز باید مدیر مخزن
تنظیم **Immutable Releases** را فعال کند. این تنظیم به ریلیزهای آینده اعمال
می‌شود و انتشار عمومی‌شدهٔ قبلی را خودکار قفل نمی‌کند.

۱. با حساب دارای دسترسی مدیر وارد [Settings مخزن](https://github.com/vahid162/gre-4/settings) شوید.

۲. در صفحهٔ General، بخش Releases را پیدا و **Enable release immutability**
را انتخاب کنید. پیش از انتشار بعدی، وضعیت ذخیره‌شدهٔ تنظیم را بررسی کنید.

اگر GitHub CLI روی رایانهٔ مدیر نصب و احراز هویت شده باشد، همین تغییر با فرمان
زیر نیز ممکن است؛ این فرمان مربوط به مدیریت GitHub است و روی سرور VPN اجرا
نمی‌شود. دسترسی Administration با مجوز write لازم است:

```bash
gh api --method PUT repos/vahid162/gre-4/immutable-releases
```

توکن را در مخزن، لاگ یا گفت‌وگو قرار ندهید. توکن معمولی CI با دسترسی انتشار
فایل‌ها الزاماً مجوز تغییر تنظیمات مدیریتی مخزن را ندارد.

روش انتشار پیش‌نویس، بارگذاری کامل و سپس عمومی‌کردن با قفل انتشار سازگار است.
پس از عمومی‌شدن، فیلد `immutable` در متادیتای همان Release و نشان Immutable
صفحهٔ آن را بررسی کنید. وجود قانون در فایل‌های مخزن، به‌تنهایی اثبات فعال‌بودن
این تنظیم در GitHub نیست.

منابع رسمی: [فعال‌سازی قفل انتشار](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes)،
[مفهوم Immutable Releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).

## تأیید نتیجه

پس از موفقیت publisher، مقصد تگ را با SHA ادغام‌شده تطبیق دهید. فایل‌های هر دو
آدرس تگ مشخص و `releases/latest` را دریافت، checksum را بررسی و محتوای اسکریپت
را با فایل همان commit مقایسه کنید. آدرس ثابت raw-main نیز باید همان ورودی
آزموده‌شده را بدهد. موفقیت merge یا ساخته‌شدن پیش‌نویس به معنی پایان انتشار نیست.
