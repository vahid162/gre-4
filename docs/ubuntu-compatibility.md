# سازگاری و آزمون Ubuntu

هدف این ماتریس، Ubuntu 22.04 LTS، Ubuntu 24.04 LTS، Ubuntu 26.04 LTS و
Ubuntu 26.10 روی معماری ثبت‌شده در اجرای آزمون است. نسخه‌های میانی که
پشتیبانی رسمی آن‌ها پایان یافته، جزو این ماتریس نیستند. این انتخاب به معنی
ادعای خرابی آن نسخه‌ها نیست.

## معنی نتیجه‌ها

- **بررسی کد و وابستگی‌ها:** ابزارها و گزینه‌های مورد استفاده بررسی شده‌اند؛
  اتصال واقعی یا بوت سیستم از این بررسی نتیجه نمی‌شود.
- **رگرسیون ایزوله:** فرمان‌های شبکه و سرویس‌ها جایگزین شده‌اند. این تست‌ها
  ترتیب تغییرات، خطاها و نگهداری وضعیت بازیابی را بررسی می‌کنند.
- **پذیرش واقعی:** کرنل، systemd، UFW و ترافیک GRE در ماشین مجازی همان Ubuntu
  استفاده می‌شوند. نتیجه فقط برای commit، نسخهٔ image و پیکربندی ثبت‌شده معتبر است.

برای تعیین وضعیت یک تغییر، نتیجهٔ jobهای همان commit در GitHub Actions و
artifactهای آن را بخوانید. job شکست‌خورده یا اجرا‌نشده، تأیید سازگاری نیست.
این سند، فهرست ثابت نسخه‌های «قبلاً تأییدشده» محسوب نمی‌شود.

## پیش‌نیاز نصب تازه

اسکریپت به Bash، systemd، iproute2، procps و util-linux نیاز دارد. نقش ایران
برای NAT به iptables نیاز دارد. UFW اختیاری است؛ اگر فعال باشد، ابزار
iptables-restore برای اعتبارسنجی تغییر فایل آن لازم است.

روی نصب حداقلی، مدیر می‌تواند بسته‌های لازم را پیش از اجرا نصب کند:

```bash
sudo apt-get update &&
sudo apt-get install -y iproute2 iptables procps util-linux kmod
```

این فرمان برای میزبان Ubuntu با مدیریت بستهٔ سالم است. خود اسکریپت بسته‌ای
نصب نمی‌کند و UFW را صرفاً برای عبور از بررسی‌ها فعال نمی‌کند.

در نقش خارج، خواندن `net.netfilter.nf_conntrack_max` پیش از تغییر forwarding
بررسی می‌شود. اگر کلید موجود باشد، وجود `modprobe` لازم نیست. در غیر این صورت،
اسکریپت در صورت در دسترس بودن فرمان، برای بارگذاری `nf_conntrack` تلاش و کلید
را دوباره بررسی می‌کند. نبود کلید پس از این مرحله می‌تواند به محدودیت محیط
یا کرنل مربوط باشد؛ آن را با نوشتن مقدار ساختگی یا حذف فایل بازیابی حل نکنید.

## تفاوت ابزارهای پایه

Ubuntuهای جدید از rust-coreutils نیز استفاده می‌کنند. آزمون باید رفتار واقعی
ابزارهای پیش‌فرض همان image را ثبت کند، از جمله `chmod --reference`،
`stat -c`، قالب‌های `mktemp`، `mv -T` و حفظ مجوزها در کپی. صرف وجود گزینه‌ها
یا GNU بودن ابزارها، نتیجهٔ تست نیست. تغییر پیش‌فرض ابزارهای سیستم برای سبز
کردن تست، باید به‌عنوان محیط متفاوت گزارش شود.

## دامنهٔ پذیرش

آزمون یکپارچگی باید شروع، توقف، شروع مجدد و بوت را با دو همتای مستقل بررسی
کند. فعال بودن سرویس یا UP بودن رابط کافی نیست؛ TCP و UDP باید از مسیر ورودی
ایران، NAT و GRE عبور کنند و پاسخ واقعی برنامه برگردد. ادامهٔ کار همتای دوم
پس از توقف یا حذف همتای اول، حفظ SSH و قواعد مدیر و بازیابی تنظیمات مشترک
پس از حذف آخرین پروفایل نیز بررسی می‌شوند.

آزمون‌های شکست در ماشین‌های موقت انجام می‌شوند. اجرای آن‌ها روی سرور دارای
ترافیک واقعی مناسب نیست. برای بررسی محدودیت‌های ارائه‌دهنده، شبکهٔ عمومی و
مهاجرت نصب قدیمی، [راهنمای پذیرش سه‌سروری](three-server-acceptance.md) نیز لازم است.

کانتینر معمولی کرنل میزبان را به اشتراک می‌گذارد؛ اجرای تست داخل image یک
Ubuntu دیگر، به‌تنهایی آزمون کرنل یا بوت همان Ubuntu نیست.

## اجرای پذیرش روی میزبان آزمایشی

این فرمان را در checkout مخزن و روی میزبان آزمایشی دارای QEMU، ابزارهای
cloud-image-utils، firmware بستهٔ ovmf، OpenSSH client و Python اجرا کنید:

```bash
python3 -B tests/integration/ubuntu_vm.py --release 22.04
```

برای نسخهٔ دیگر، مقدار `--release` را به `24.04`، `26.04` یا `26.10` تغییر دهید.
این اجرا تصویر رسمی Ubuntu را دریافت و checksum آن را بررسی می‌کند، سپس سه
ماشین مجازی موقت می‌سازد. بسته‌های سرویس و فایروال داخل مهمان نصب می‌شوند.
شبکهٔ آزمایش به ماشین‌های موقت محدود است؛ نیازی به تغییر bridge یا فایروال
میزبان ندارد. با KVM سریع‌تر است؛ اجرای بدون شتاب‌دهی به زمان بیشتری نیاز دارد.

نتیجه‌ها در `dist/ubuntu-<release>/` نوشته می‌شوند؛ در CI همین پوشه به‌عنوان
artifact نگهداری می‌شود. کلید خصوصی SSH آزمایش نباید داخل این پوشه یا Git باشد.
پوشهٔ نتیجه، حتی در صورت شکست، برای تشخیص مرحلهٔ ناموفق بررسی شود. آزمون‌ها
فقط در مهمانی که نشان مخصوص محیط موقت را دارد اجازهٔ تغییر شبکه و سرویس می‌دهند.

## شواهدی که باید نگه داشت

برای هر اجرا، commit، نسخه و checksum تصویر Ubuntu، نسخهٔ کرنل، Bash، systemd،
iproute2، iptables، UFW، پیاده‌سازی coreutils و نتیجهٔ موارد پذیرش ثبت شود.
گزارش‌ها باید فاقد کلید SSH، اطلاعات کاربران و تنظیمات میزبان‌های عملیاتی باشند.
بررسی دامنهٔ پشتیبانی در ایشو #14 و اصلاح‌های اجرایی مرتبط در ایشوهای #12 و #13
پیگیری شده‌اند؛ بسته‌شدن یک ایشو جای شواهد اجرای واقعی را نمی‌گیرد.
